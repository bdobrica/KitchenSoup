# Milestone 14 — Model registration and lineage

Date: 2026-10-19

## Implemented

- Successful new training output registers a logical model/version, LoRA adapter
  artifact, parent relationship and retained source/license provenance.
- A unique nullable training-run foreign key binds the result version to its run;
  run/model responses expose additive result, parent and artifact identifiers.
- Committed POSTPROCESSING survives interruption. Deterministic result identities,
  object keys and ZIP bytes support registration retry without relaunching training,
  duplicating versions or prematurely recording SUCCEEDED.
- The local executor provides a bounded inert ZIP stream, verifies container/runner
  identity and rehashes confined regular adapter files during copying. Artifact
  SHA-256, size and format cover the exact downloadable bundle; the embedded
  manifest retains individual output hashes.
- Separate ancestor graph APIs cover models and artifacts. Artifact inputs include
  the exact uploaded base when applicable, dataset manifest and examples, with
  existing upstream dataset derivations preserved. Both graphs reject cycles and
  edge rewrites in PostgreSQL; trained model identity cannot be reassigned.
- Model/artifact detail views show lineage through packaged SVG rendering and
  generated Mermaid data. Source/license provenance remains visible. Trained
  models appear in selection and the use-as-base flow selects the exact version.
- Lazy base requirement detection explains adapter-only merge requirements before
  further training; plan review rejects unsupported use rather than substituting
  ancestor weights. Actual merge execution remains Milestone 17.

See [ADR 0015](../adr/0015-training-output-lineage.md) and
[the model reference](../models.md#trained-models-and-lineage).

## Verification performed

- Relational migration generated by Alembic against disposable PostgreSQL; SQL
  lineage/identity guards are in a separate hand-authored revision. No generated
  artifact was manually edited; `make openapi` regenerated the v1 HTTP schema.
- Focused `tests/unit/test_local_executor.py` passed: **6 tests**, including stable
  output ZIP bytes and rejection when adapter bytes change after status verification.
- `make verify` passed: Ruff formatting/lint, strict mypy over **103 source files**,
  generated-schema equality and **276 unit tests**.
- `sg docker -c 'make test-integration'` passed: **62 integration tests** against
  disposable PostgreSQL 18.6, RustFS beta.12 and Valkey 9.1.1. No Docker daemon/group
  permissions were changed. Disposable containers are removed by the harness.
- Registration checked for both public-revision and uploaded base models, including
  exact ZIP contents/hash/size, output links, inherited license URL/notes/revision,
  and preservation of the reviewed license despite a later source metadata change.
- Database checks cover one result per run, immutable result/run identity, transitive
  model/artifact cycles, append-only edges, full migration round trips, idempotent
  upgrades and Alembic metadata drift.
- A lost object-write acknowledgement leaves POSTPROCESSING without partial registry
  metadata. A fresh service registers the same object key and hash, creates one
  result, records SUCCEEDED once and does not submit another external job. Duplicate
  delivery during import is excluded by the existing per-run claim. Run and event
  reads finish while registration's write transaction is still open.
- API lifecycle checks confirm separate model/artifact graphs, upstream derivations,
  missing roots, model-list visibility, full-source readiness, adapter merge
  requirements and rejection of adapter-only training-plan review. Parent/artifact
  graphs use separate identifiers; user-controlled labels do not enter Mermaid text.
- Updated browser scripts passed JavaScript syntax checks in V8. Model/artifact HTML
  routes were exercised through the HTTP test client. No frontend dependencies added.
- Final diff reviewed for unrelated changes, generated drift and sensitive payloads.

## Limits

External Docker training is synthetic in this validation. No GPU training, numerical
model-quality check, new model download, live provider call or browser end-to-end
rendering test was performed. Prior RTX 2070 SUPER FP16 evidence remains in
[FP16 validation](fp16-training.md); runner contracts and GPU launch arguments are
unchanged. BF16 validation remains optional.

The retained application database was not migrated or populated. Apply migrations
and restart host web/worker/reconciler before using this version. Existing terminal
runs are not retrospectively registered. Keep the workspace, image, daemon and
object store available through POSTPROCESSING. Storage failures are retried by the
reconciler; orphan retention and automatic merges remain future work.
